## 一、背景与目标

### 1.1 项目定位

将 `zEngine`（游戏服务器引擎）与 `zMmoServer`（分布式 MMORPG 服务端）从"设计完整但实现半成品"的现状，改造为**能真正上线一款游戏、同时可作为可复用开源框架对外发布**的成熟可靠框架。

这是一个**双目标**定位，标准比"能跑就行"高：

- **上线游戏**：要求运行时正确性、可靠性（断线重连/一致性/持久化）、可运维（监控/日志/告警）。
- **开源框架**：要求单一清晰的实现（无死代码/无两代并存）、稳定的对外契约、文档与代码一致、可被第三方无痛复用。

### 1.2 现状定级（已核实）

> 以下为 2026-07-23 通过**通读文档 + 逐模块代码核对 + 实际编译**得出的真相基线，不采信项目自评。

- **编译状态**：`zUtil`、`zEngine` 编译通过；`zMmoServer` 为**多模块仓库**（`zCommon/GlobalServer/GatewayServer/GameServer/MapServer/GameClient` 各自独立 `go.mod` + 根 `go.mod`，无 `go.work`），六模块**全部编译通过**。
- **设计成熟度**：高。分组跨服、三种地图模式、2PC 玩家迁移、Outbox/Inbox 一致性、AOI、ECS 组件化——蓝图认真且完整。
- **实现成熟度**：**显著低于项目自评**。自评报告称"端到端集成测试全绿（登录→创角→进图→移动→攻击→登出）、综合 4.91/5"，但代码核对证明 **GameServer↔MapServer 核心链路在当前代码下是断的**（详见第二节）。自评的"进图成功"实为 GameServer 本地伪造响应，玩家从未真正进入 MapServer 的地图。

**结论**：本项目最根本的问题不是某个功能缺失，而是**"文档/自评与运行现实严重脱节"**。因此改造的第一原则是"真相优先"——一切成熟度必须由可跨进程断言的集成测试背书。

## 二、已核实的核心缺陷

### 2.1 阻断级：GameServer↔MapServer 链路断裂（三重独立断裂，各自即可致命）

从源码直接确认（`GameServer/game/maps/map_service.go`、`MapServer/net/service/tcp_service.go`）：

1. **protoId 语义错位**：GameServer 四类请求（enter/leave/move/attack）全部以 `protoId=300` 发送（map_service.go:430/496/582/724），而 MapServer 只 `switch` 认 `400/402/404/406`（tcp_service.go:150-160），`300` 必落 default「unknown message」。
2. **编码互不相认**：GameServer 用 `proto.Marshal` 打包 `CrossServerMessage`（map_service.go:294），MapServer 用 `json.Unmarshal` 解（tcp_service.go:143）——以 JSON 解 protobuf 字节，先于 protoId 判断即失败。
3. **双重封装 + 坐标丢失**：`sendMapEnterRequest` 已打包一次 `BaseMessage`，`sendMapMessage` 又套一层 `BaseMessage{MsgId:300}`；且内层用 `ClientMapEnterRequest`（无坐标），而 MapServer 期望 `MapEnterRequest`（含 XYZ）。
4. **同步 Attack 通道无人填充**：`HandleMapAttackResponse` 未被任何回程接收器调用，`sendMapAttackRequest` 的 1500ms 等待必然超时。

### 2.2 结构级：两代重构并存 + 死代码

- GameServer/MapServer 各有 `net/service`（在用）与 `connection`（死代码）**两套连接实现**并存。
- MapServer 的 **skill/economy/quest/item 五大系统无任何网络 protoId 入口**，仅内部/测试可达——即"已完成"但对外是死的。
- 端口（20002/30001）、固定 mapIDs 列表均硬编码。

### 2.3 引擎级：zEngine 框架缺陷（核实）

1. **无 `protoId→handler` 注册表**：全框架只有单个 `HandlerFun` dispatcher，协议分派要业务自己写 switch。
2. **加密/压缩顺序不对称**（发 enc→compress，收 dec→decompress），组合逻辑错误，仅因 GCM 密文压不小而未暴露。
3. `option.go` 用 `reflect.TypeOf().String()` 字符串匹配分发选项，脆弱不可扩展。
4. zActor 邮箱满**静默丢消息**；`Stop()`/`SendMessage` 有向已关闭 channel 发送的 TOCTOU 隐患；`SetSelf` 漏调则静默退化。
5. zEvent `Unsubscribe` 未实现。
6. README 描述的 `zSystem`(ECS) 模块**实际不存在**。

### 2.4 一致性/信息级偏差

- 跨服 Envelope Magic 实际是 `0x5A4D4D4F`（"ZMMO"），文档误写 `0x5A4D4F4F`；40 字节头只用到偏移 38。
- crossserver RPC 载荷用 JSON 而非 protobuf。
- Outbox/Inbox 为纯内存实现，进程重启丢在途消息。

## 三、已确定的关键决策

| 决策 | 结论 | 理由 |
|------|------|------|
| **框架用途** | 上线游戏 + 可复用开源框架（双目标） | 标准取两者更高者：既要运行时可靠，也要单一清晰契约 |
| **Game↔Map 统一实现** | 保留 `net/service` + **全程 protobuf**；删除 `connection` 死代码那套 | `net/service` 是实际在用路径；protobuf 与协议定义一致，去掉 JSON 混用 |
| **领域逻辑权威** | 以 `zCommon/game` 为**单一权威**，各 server 改为引用 | 共享层单一真相源，最符合开源框架定位；消除 buff/skill/item/quest 双份实现 |

### 三.1 领域逻辑分层（Phase 4.1 勘察后细化）

实施 4.1 时发现「消除双份实现」不能字面理解——两边并非"同一逻辑抄两份"，而是**不同层次**：

| 层 | 位置 | 职责 | 举例 |
|----|------|------|------|
| **领域模型 + 权威类型** | `zCommon/game` | 领域概念的**规范类型**与轻量模型；GameServer 玩家 Actor 状态用它 | `ItemType`/`ItemRarity`/`EquipSlot`/`SkillType`/`SkillStatus`/`BuffType`、`Buff`/`Skill`/`Item`/`Inventory`/`Equipment` 结构 |
| **战斗权威运行时** | `MapServer/maps/*` | MapServer 作为战斗权威的**表驱动运行时**，配置来自 excel（Buff.xlsx 等），含效果计算/叠层/AOE 等运行时机制 | `maps/buff`(BuffEffect 17 种效果+ActiveBuff)、`maps/combat`(DamageType)、`maps/skill`、`maps/loot`、`maps/economy` |

**准则**：
- **同义原语必须单一定义**：概念相同、语义一致的类型枚举只在 `zCommon/game` 定义，MapServer 引用（别名/直接引用），杜绝静默分歧。已统一：`ItemType`/`ItemRarity`（此前 object 包与 game 各定义一份同值枚举 → 改 object 别名再导出 game 版）。
- **不同职责合理并存**：MapServer 的表驱动战斗运行时（BuffEffect、combat、loot、economy）是权威侧独有机制，**不**塞回 `zCommon/game` 骨架、也不删——强行合并会降级运行时且高风险。
- **语义分歧暂不强并**：如 `BuffType`（game=Positive/Negative/Neutral vs MapServer=None/Buff/Debuff/Neutral，且 MapServer 运行时实际用字符串 "stun"/"poison"），强行统一会碰配置映射，低价值高风险，暂留并登记。

## 四、指导原则

1. **真相优先**：停止相信自评。任何"完成"必须由**能跨进程断言下游真实状态**的集成测试背书（玩家真的在 MapServer 的 `map.objects`、AOI 真的推包、attack 真的改 HP），禁止本地伪造响应。
2. **单一实现**：每个能力只留一套，删掉另一套。两代并存是当前最大隐患。
3. **契约集中**：protoId、消息结构、编码方式必须有唯一真相源，任何一处不一致视为 bug。
4. **能力上收引擎**：底层缺陷在 zEngine 修，业务层不写 workaround（这正是 `project_rules.md` 已写但未落实的原则）。
5. **门禁不可跳**：每阶段出口 = 真集成测试全绿 + `-race` 干净 + `golangci-lint` 通过，缺一不合并。

## 五、改造路线图（五阶段）

> 详细任务分解见 [成熟化改造-执行计划.md](成熟化改造-执行计划.md)。

### Phase 0 — 建立真相基线（阻塞一切的前提）

- CI 门禁：多模块 `build + vet + test -race + lint`。
- 真·集成测试框架：断言落到下游进程真实状态。
- 修复 Game↔Map 断链（protoId/编码/结构/attack 回程）。
- 删死代码：`connection` 两套二选一。

**出口**：一个玩家能真正在 MapServer 上进图→移动→打怪→怪掉血→掉落/重生，全部由集成测试断言、race 干净。

### Phase 1 — zEngine 引擎层硬化

- zNet：引入 `protoId→handler` 注册表；修加密/压缩顺序；去 option.go 反射字符串匹配；明确 worker pool 与 FIFO 取舍。
- zActor：邮箱背压可配 + 丢弃指标；Stop/SendMessage 并发安全；SetSelf 构造函数内强制。
- zServer：状态机与 Start/Stop 联动或明确文档化。
- zEvent：实现 Unsubscribe。
- 补齐引擎单测 + race；清理失实文档（zSystem 等）。

### Phase 2 — zMmoServer 契约与一致性统一

- 协议单一真相源（protoId/结构/编码集中，全 protobuf）。
- 统一 Game↔Map 传输并防回归。
- 打通 MapServer 侧 AOI→GameServer 事件回程。
- 补齐 skill/economy/quest/item 网络入口。
- 去硬编码（端口/mapIDs 进配置并与 Excel 校验）。

### Phase 3 — 可靠性与可运维

- Gateway 自动重连 GameServer + 会话恢复。
- Game↔Map 连接去重 / 健康检查 / 断线重连。
- Actor 监督策略接入业务。
- Outbox/Inbox 可持久化（重启不丢在途消息）。
- 可观测性：zMetrics 接入 zNet；trace_id 全链路贯穿。

### Phase 4 — 消重与文档对齐（开源发布就绪）

- 消除 GameServer/MapServer 子系统 vs `zCommon/game` 重复（以 zCommon 为权威）。
- 重写评估报告为"可验证事实"（每条"已完成"挂一个通过的集成测试）。
- 开源发布准备：README/快速开始/架构文档/贡献指南与代码对齐；LICENSE/示例。

## 六、成熟框架验收标准（Definition of Done）

一个"成熟可靠、可上线可开源"的框架，须同时满足：

1. **正确性**：全链路（登录→创角→进图→移动→战斗→掉落→登出→重连）由真集成测试断言，跨进程效果可见。
2. **可靠性**：任一下游进程重启，上游自动重连并恢复；在途消息不丢（持久化 Outbox/Inbox）；Actor panic 可恢复。
3. **单一实现**：无死代码、无两代并存；每能力一套。
4. **契约稳定**：协议/编码单一真相源；对外 API 有版本与兼容策略。
5. **可运维**：指标（Prometheus）、日志、trace_id 全链路；健康检查真实反映状态。
6. **质量门禁**：`build + vet + test -race + lint` 全绿，核心链路测试覆盖达标。
7. **文档一致**：所有对外文档与代码实测一致，无失实描述。

## 1. 全景：四类进程组成一个"服"

```
                    ┌──────────────┐
                    │ GlobalServer │  账号 / 服务器列表 / 服务发现中枢（无游戏态）
                    └──────┬───────┘
                           │ etcd 服务发现（按 GroupID 分组）
        客户端 ──TCP──▶ ┌──▼──────────┐
                        │GatewayServer│  连接 / 鉴权 / 消息路由（无游戏态）
                        └──────┬──────┘
                               │ 1:1
                        ┌──────▼──────┐
                        │ GameServer  │  玩家逻辑 + 持久数据权威（落库）
                        └──────┬──────┘
                               │ 1:N
                 ┌─────────────┼─────────────┐
            ┌────▼────┐   ┌────▼────┐   ┌────▼────┐
            │MapServer│   │MapServer│   │MapServer│  空间 / 战斗 / AOI / tick
            │ (主城)  │   │ (副本)  │   │ (野外)  │  瞬时模拟权威（不落库）
            └─────────┘   └─────────┘   └─────────┘
```

一句话理解：**客户端只连 Gateway**；Gateway 把消息转给 GameServer 处理玩家逻辑；需要空间/战斗的部分下沉到 MapServer；GlobalServer 只管账号和"有哪些服"。**这一整套 = 一个"服（realm）"**，扩容就是再开一套。

---

## 2. 为什么是 realm（而不是全区全服）

**realm = 每个服自成一个完整世界**（像魔兽的一个"服务器"、传奇的一个"区"）。玩家选一个服进去，就在那个世界里玩；不同服的世界互相独立。

- **扩容 = 加一个 realm**：新开一套 `{GameServer + 它的 MapServer 们 + 独立数据库 GameDB_区服ID + 服务器列表里加一行}`，与现有服完全隔离。不是把所有人塞进一个巨型全区全服集群。
- **为什么这么选**（对比全区全服）：
  - **隔离** —— 一个服的库崩/进程崩，不影响别的服；数据默认"本服内"，心智简单。
  - **线性扩容** —— 承载翻倍就加一个服，不需要重构。
  - **代价** —— 跨服玩法（跨服战场/BOSS）要**专门设计**，不是自动就有（见 §7）。
- 这个选择贯穿全架构：**数据库 per-realm**、**服务发现按 GroupID 分组**（一个 GameServer 只发现本组的 MapServer）。

> realm 内部想变大（一张主城挤爆）也有办法，但走的是"分线/无缝/实例"（§6），仍在**单服内**，不破坏隔离。

## 3. 四类进程各干什么

| 进程 | 职责 | 有无游戏态 |
|------|------|-----------|
| **GlobalServer** | 账号注册/登录、JWT 签发、服务器列表、服务发现中枢 | **无**（别往里塞玩法，它要保持轻、好重启） |
| **GatewayServer** | 客户端 TCP 连接、鉴权、把消息路由到 GameServer | **无**（纯转发/安全层） |
| **GameServer** | 玩家逻辑、**持久数据权威**（背包/货币/等级…）、进出图协调 | **持久态**（唯一落库者） |
| **MapServer** | 地图实例、AOI 视野、战斗、AI、100ms tick | **瞬时态**（血/位/buff，不落库） |

**拓扑：1 Gateway ↔ 1 GameServer ↔ N MapServer。** 为什么 GameServer 只带一个 Gateway、却带 N 个 MapServer？——一个服的"玩家逻辑中枢"是一个（GameServer），但地图很多、战斗吃 CPU，于是把地图摊到多个 MapServer 分担算力。

---

## 4. 最重要的一课：玩家的"两个化身"与权威分层

**这是理解本架构的钥匙。** 一个在线玩家，同时存在于两个进程、有两个对象：

| | 在哪 | 管什么 | 生命周期 |
|--|------|--------|---------|
| **持久业务权威** | GameServer 的 `player.Player`（Actor） | 背包 / 技能 / 货币 / 钻石 / 经验 / 等级 / 任务 / 仓库 / 邮件 | 跨登录持久，**落库** |
| **瞬时模拟权威** | MapServer 的 `object.Player` | 血量 / 位置 / 朝向 / 战斗内 buff / 仇恨 | 随进出图/战斗存续，**不落库** |

**为什么要拆成两个？** 战斗时血量/位置每帧都在变（高频），放在 MapServer 本地跑最快；而背包/货币这类"钱袋子"绝不能两个进程都能写（双写者 = 覆盖/丢失/不一致）。所以：**持久的东西只有 GameServer 能写库，瞬时的东西 MapServer 自己算。**

数据怎么在两者间流动：

```
登录    客户端 → Gateway → GameServer：从 DB 载入玩家持久数据到 player.Player(Actor)
进图    GameServer →(只读快照:等级/攻防/技能)→ MapServer：初始化 object.Player
战斗    MapServer 本地算血量/位置/掉落（瞬时，快）
回流    击杀掉落/经验(持久变更) → MapServer 打成 AttrGrant 事件 → 回 GameServer 落库
```

**两条铁律**（违反 = 数据错乱，本项目踩过）：
1. **MapServer 绝不直接写库**；一切持久变更走 `AttrGrant` 事件回流到玩家的家 GameServer。
2. **回流幂等**：每条 grant 带唯一 `requestID`，接收方去重——重投（重连/崩溃恢复）不会把奖励算两次。

> 进场快照是**只读**的，不是"第二权威"——MapServer 拿它初始化战斗数值，改的是瞬时态，持久变更仍走回流。

## 5. 地图怎么跑：单写者 Actor + AOI + tick

**每张地图 = 一条独立的 goroutine（单写者 / Actor 模型，代号 MAP-2）。** 所有会改动地图对象状态的工作——网络命令（进入/移动/攻击）和帧更新（AI/战斗/buff）——都投递到这条 goroutine 上**串行执行**。

- **为什么**：MMO 地图上，AI、战斗、玩家请求、刷怪都在**并发**改同一批对象。用锁：容易死锁、容易漏保护一个字段就是数据竞争。单写者把"并发改共享状态"变成"排队改"，从根上消除竞争——最简单也最稳。
- **规则**：碰对象字段必须在这条 goroutine 上（经 `Map.Do`）；绝不在网络 goroutine 上裸读写对象字段。

**AOI（Area of Interest，兴趣区域）**：玩家不需要知道整张地图，只需要"看得见的范围"内发生了什么。网格 AOI 把地图切成格子，只把**视野内**实体的变化（进入/离开/移动/血量/死亡/buff）推给你。客户端视野**只由 MapServer 的 AOI 单一权威驱动**（历史上曾另建一套导致串视野，已根治）。

**tick**：每张地图 100ms 一帧，驱动 AI / buff 到期 / 技能等周期逻辑。

## 6. realm 内怎么伸缩：分线 / 无缝 / 实例

一张热门地图人太多，而"一张图 = 一条 goroutine = 一核封顶"怎么办？三招——**都在单服内，不碰全区全服**：

- **分线（Layering）**：热点图开多个平行副本（"层/线"），玩家分摊进去、跨层互不可见。魔兽的 layering。填满 softCap 就开新层，空层自动回收。
- **无缝（Seamless）**：连续大陆的相邻分区之间，玩家走过区界时被**透明交接**给下一张图，实时态随身带、不重登、无 loading。魔兽的无缝世界。**只有登记为无缝邻居的图对才走**，否则回落普通切换。
- **实例（Instance）**：副本 / 战场 / 跨服临时图，统一的生命周期（按需创建、空了自动回收、不泄漏 goroutine）。

三者**同构**：本质都是"派生一张独立的 `*Map`（独立 goroutine + 独立 AOI + 独立 tick）"，复用同一套实例基础设施。细节见 [realm架构-详细设计.md](realm架构-详细设计.md)。

## 7. 跨服怎么做：临时实例 + 回流（不破坏 realm 隔离）

realm 默认是隔离的。要做跨服玩法（跨服战场、跨服 BOSS）时：

- 开一个 **`CrossServer` 类型的临时实例**，把来自多个服的玩家放进去打。
- 结果（战斗/奖励的持久变更）**按玩家归属 `AttrGrant` 回流各自的家服**落库——跨服实例只产事件、不碰持久资产。
- 打完人走，实例空置自动回收。

**关键**：这不是全区全服——平时各服各玩各的，只在跨服活动时**临时汇合**。低人口服的"合并"是另一套机制（互联服，见 realm 方向文档 §5.2）。

## 8. 状态怎么保证不丢：Outbox/Inbox + 幂等

跨进程消息（尤其回流、发放）会遇到重投、丢失（网络重连、进程崩溃）。两层保障：

- **幂等**：加性变更（加经验/货币/物品、回流结算）都带 `requestID`，接收方 `TryAccept` 去重——重投不翻倍；消耗类在 Actor 里校验余量（CAS），不足则拒绝，不会扣成负数。
- **崩溃安全**：关键在途消息可走 `zCommon/consistency` 的 **Outbox/Inbox 持久化**，进程重启后重放未完成的消息——"结算完但还没落库时崩溃"的窗口也堵上。

## 9. 其它地基（简要）

- **服务发现**：etcd，按 `GroupID` 分组——一个 GameServer 只发现本组 MapServer，这是 realm 隔离在服务发现层的落地。
- **ID 体系**：`ServerID` = 6 位语义 ID（GroupID 4 位 + ServerIndex 2 位，如 `000101`）；运行时 ID 用 Snowflake（PlayerId/ObjectId）；配置 ID 用 int32（MapId/SkillId）；另有 20+ 类型化 ID 防混用。ServerID **不进业务主键**（用 Snowflake），为将来合服不撞 ID 留余地。
- **通信**：Gateway↔Game↔Map 全 protobuf；跨服消息经**唯一编解码源** `zCommon/crossserver/codec.go`（线格式契约见 [协议契约.md](协议契约.md)）。

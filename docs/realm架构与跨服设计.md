# Realm 架构与跨服设计

> 本文确定 zMmoServer 的分服/跨服**架构定位与演进方向**。核心结论：本项目是 **realm-based（按服自成一世界）** 的架构，
> 与「魔兽世界 / 传奇」同源，而**不是**「全区全服」模型（后者见 dragonsvr）。两者是不同的架构哲学，不存在谁更"成熟"，
> 只有"是否匹配定位"。本文用魔兽世界（WoW）的 realm 架构作参照，给出与该定位一致的建议。

## 0. 一句话定位

**一个「服」= 一个自成一体的完整世界（realm）。** 玩家登录后选服、进入某个 realm，其角色数据、经济、社交都
**默认锁在这个 realm 内**。跨服是**例外、可选、临时**的（跨服战场/BOSS、低人口互联服），而不是常驻的全局层。
**水平扩展 = 开更多 realm，而不是把一个服做成全区全服。**

---

## 1. 为什么是 realm 模型（而非全区全服）

| | Realm 模型（本项目 / WoW / 传奇） | 全区全服模型（dragonsvr） |
|---|---|---|
| 世界边界 | 每服一个独立世界 | 无"服"概念，逻辑分服=元数据 |
| 数据 | 每服独立库（`GameDB_区服ID`） | 服组分片、`scope_id` 经济边界 |
| 经济/社交 | 默认锁在本服 | 全区全服（交易行/匹配/名片全局） |
| 跨服 | 例外：临时实例 + 低人口互联服 | 常态：全局层 + 事件总线 |
| 扩展方式 | **加服** | 加副本/加分片/动态归属 |
| 合服 | 互联服（Connected Realms） | 重指 `scope_id`、零迁移 |

选 realm 模型的后果是好的：架构清爽、每服自洽、故障隔离（一个服挂不影响别服）、可通读。代价是"全区社交/经济"做不了——
但这**正是设计取舍**，不是缺陷。

---

## 2. 现状对照：zMmoServer 已经符合 realm 范式的部分

以下都**正确、不需要改**（曾一度被误判为"待优化"，此处澄清）：

- **每服独立库** `GameDB_区服ID`（如 `GameDB_000101`=1 区 1 服），GlobalDB 独立 —— 对应 WoW 的 realm 角色库。**对。**
- **登录 = Realm-List 模式**：GlobalServer 管账号/JWT + 服务器列表；客户端两阶段登录、选服、连该服网关 —— 对应 WoW 的 Auth + Realm List。**对。**
- **GameServer = realm 世界权威 + MapServer 1:N**：GameServer 是本服协调/持久权威，MapServer 经 etcd 发现、`mapID→serverID` 路由、真 1:N —— 对应 WoW 的 worldserver + 多 map 进程分布。**对。**
- **Gateway↔GameServer 1:1**：一个 realm 就是一个 world 权威，**不需要**"多 GameServer 负载均衡"。要承载更多玩家就**开更多服**。**对，不该解 1:1。**
- **副本 = 实例地图**（instance map，含本项目已做的实例生命周期清理）—— 对应 WoW 的 dungeon/raid 实例。**对。**
- **`cross_group` 共享地图**：多个（同组）服的玩家可共享一张图，MapServer 记每个玩家的 origin GameServer 回路 —— 这是"跨服临时实例"的**雏形**（见 §5）。

> 澄清：`GameDB_区服ID`「把身份焊在物理库」在**全区全服模型下**是反模式，但在 **realm 模型下是标准做法**。定位不同，结论相反。

---

## 3. WoW realm 内部伸缩三招（都不涉及全区全服）

魔兽一个 realm 内部承载靠这三招，正是 realm 模型该发力的地方：

### 3.1 地图分布 + 无缝交接（Seamless World）
魔兽大陆无缝：玩家走过区界，服务器把他**透明交接**给拥有下一张图的 map 进程，实时态随身带走，只有跨大陆/进副本才 loading。
这是"单服却世界很大"的关键。

### 3.2 热点区动态分线 / 分层（Sharding / Layering）
处理开放世界爆满：给**同一张图开多份平行副本（层）**，玩家分摊进去，跨层互不可见。这是纯单服的伸缩技术。

### 3.3 该隔离的一律实例化（Instancing）
副本、团本、战场、竞技场都是独立实例，用完即毁。

---

## 4. 重定向建议（把单个 realm 做深）

### 建议 ①｜补无缝地图交接（最高价值的单服增强）
**现状**：MapServer 已 1:N，但地图切换大概率是离散的 enter/leave（进图/离图），跨图不平滑。
**目标**：玩家跨区界 → GameServer 协调，把其在旧 map 的实时态（位置/血量/战斗态）**平滑迁移**到新 map，客户端不断线、无二次登录。
**落点**：在 GameServer 的 `MapServerManager`（`mapID→serverID` 路由）之上加一层"地图交接事务"——旧 map `LeaveMap`(带状态快照) → 新 map `EnterMap`(恢复快照) → 切换玩家的 map 归属与 AOI。参考本项目已有的跨图请求链（`internal.proto` 400 段地图请求/响应）。
**价值**：让单个 realm 的"世界感"上台阶，是最"魔兽味"的改进。

### 建议 ②｜热点图动态分线（Layering）
**现状**：每张 map 由单 goroutine 串行驱动（`MapServer/maps/map_actor.go` 的 `Map.Do` 同步投递 + 100ms tick），**一张热图卡在一核封顶**（约千级 CCU 天花板）。
**目标**：同一张开放世界图允许**多实例（层）并存**，玩家按负载分摊到不同层，AOI 按层隔离、跨层互不可见。
**落点**：`MapManager` 已能按 `mapID` 管理多图；扩展为"同一逻辑 mapID 可有多个 layer 实例"，进图时按人数/负载分配 layer。这直接把单 map 单核瓶颈**横向摊到多核/多进程**——而且**仍是单服内的伸缩，不是跨服**。
**价值**：这才是 realm 该有的水平扩展轴——**在 Map 层，不在 GameServer 层**。

### 建议 ③｜实例生命周期做干净
**现状**：本项目已做实例地图按需创建 + 空图清理（`MapManager` 统一 Cleanup+StopActor+停 spawnLoop）。
**目标**：把副本/战场统一成"按需拉起、队伍绑定、空了销毁"的干净实例，作为 §5 跨服临时实例的基础设施。

### 建议 ④｜把"两份玩家表示"讲成一条原则，而不是去合并它
**现状（结构症结）**：GameServer 持有 `player.Player` actor（持久权威：背包/技能/货币/任务），MapServer 持有独立的 `object.Player`（战斗权威：血量/位置/buff），两者是**两份独立表示、部分单向同步**——战斗产生的持久变更曾整体丢失（见 F-2）。
**不要做**：把两者揉成一份"活权威"——那是大重构，风险高、收益不确定。
**要做**：**把边界定成原则**，让分工正当化：
- **GameServer = 持久业务权威**（背包 / 技能 / 货币 / 任务）
- **MapServer = 瞬时模拟权威**（血量 / 位置 / 战斗内 buff）
- **战斗产生的持久变更一律走单向事件回流**（crossserver push），由 GameServer actor 落库。

**F-2 的正确定位**：它不是"打补丁"，是这条原则的**第一块落地**——`ExpGrantNotify`(crossserver 507) 把战斗经验从模拟侧回流到持久侧 actor。后续凡是"战斗改了需要持久的属性"（掉落已有 506、经验 507），都走同一形态的 grant 通道，而不是让 MapServer 直接写库。这样两份表示是"业务 vs 模拟"的合理分工，只要回流通道干净就不是 bug。

### 建议 ⑤｜扩展 = 加服，不是改架构
保持每服独立库 + Gateway↔GameServer 1:1。承载翻倍 = 再开一个 realm。这是魔兽/传奇的水平扩展方式，也让架构保持清爽。**不要**为了扩展去解 1:1 或建全区全服层。

## 5. 跨服设计——按魔兽 / 传奇的方式（要做时）

realm 模型里跨服是**例外、可选、临时**，绝不是常驻全局层。两种正统做法：

### 5.1 跨服临时实例（跨服战场 / 跨服 BOSS / 跨服副本）
- 把**多个服的玩家汇进一个临时实例**打（对应传奇"跨服战"、WoW 跨服战场/CRZ）。
- **不共享任何持久状态**；实例是临时的，打完即毁。
- 结果 / 奖励**结算回各自的服**——由玩家的**归属服**消费"结果事件"完成落库。
- **落点**：本项目 `cross_group` 共享地图（MapServer 记 origin GameServer 回路）正是雏形。把它做成「按需拉起的跨服实例 + 结果事件回流」即可。传输走已有 Envelope + CrossRouter；**结果回流走已有的崩溃安全 Outbox/Inbox（`zCommon/consistency`，进程重启不丢在途消息）**——这是现成地基，目前尚未接跨服业务，是很自然的下一步。

### 5.2 互联服（Connected Realms）——低人口服的解法
- 魔兽给低人口 realm 的办法：把几个物理服**逻辑上并成一个**（共享经济 / 组队 / 公会），但**不合并数据库**、角色**保留原服身份**。
- 这才是"身份 / 数据边界解耦"该出现的地方——**只在合并低人口服时按 realm 粒度用**，而**不是**当默认底座。

### 5.3 跨服红线（与魔兽一致）
- **跨服实例只产事件、不碰持久资产**；资产结算永远由玩家的**归属服**消费事件完成。
- **经济 / 社交默认锁在本服**（交易 / 公会 / 拍卖 realm-绑定，如 WoW 的拍卖行）。
- 跨边界"读"（如看别服玩家信息）用**投影 / 快照**，不做实时跨服同步 RPC。

---

## 6. 明确不做的

- **不建全区全服 fabric**（常驻的全局聊天 / 交易 / 匹配层）——那是 dragonsvr 的路，与 realm 定位冲突。
  - 注意：当前"世界聊天"是本 GameServer 内扇出（`PlayerManager.BroadcastMessage` 遍历本服在线）——在 realm 模型下**这是对的**（世界频道本就是"本服世界"），无需改成全局。
- **不为"统一"去大重构两份玩家表示**——定成"业务权威 / 模拟权威 + 事件回流"原则即可（见建议 ④）。
- **不解 Gateway↔GameServer 1:1**——realm 模型里它是对的。
- **不引入 `scope_id` 当默认底座**——只在互联服合并时按 realm 粒度用（§5.2）。

## 7. 分阶段路线（按性价比）

| 阶段 | 做什么 | 价值 | 工作量 |
|------|--------|------|--------|
| **1** | 建议 ④：把"业务权威 / 模拟权威 + 事件回流"定成原则并补齐战斗→持久回流通道（F-2 已起头） | 消除结构性数据丢失，边界清晰 | 中 |
| **2** | 建议 ②：热点图动态分线（layering） | 治单 map 单核天花板，realm 内真伸缩 | 中—大 |
| **3** | 建议 ①：无缝地图交接 | 单服"世界感"上台阶 | 大 |
| **4（按需）** | §5.1 跨服临时实例（复用 cross_group + Outbox/Inbox 结果回流） | 演示"跨服=临时实例+事件回流" | 中 |
| **5（远期/按需）** | §5.2 互联服合并低人口服 | 运营手段 | 大 |

> 原则：每一项做一个**能跑通的最小闭环**即可，不追求生产级完整度——教学骨架的价值是"把 realm 架构思想讲清楚"。

## 8. 附：与全区全服（dragonsvr）的对照小结

- dragonsvr = **全区全服**：`scope_id` 经济边界、Hub 单写者持久权威、全局层（交易行/匹配/名片）、服组分片、Placement 动态归属、跨服事件总线。为百万级、单一大市场设计。
- zMmoServer = **realm-based**：每服自成世界、每服独立库、经济社交锁本服、跨服=临时实例+互联服、扩展=加服。为"多个独立世界"设计，与 WoW/传奇同源。

**两者都对，取决于产品要"一个大世界"还是"许多个独立世界"。** 本项目选后者。

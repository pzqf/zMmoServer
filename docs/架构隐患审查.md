## 发现

### F-1 🟡→[已警示，全对齐 descope] DAO ↔ 真实表 schema 系统性失配（5/6 DAO 全错，但当前 0 运行时调用）

对比各 DAO 的 INSERT 列 vs 线上 GameDB 真实列：

| DAO | 写了不存在的列 | 真实表列 | 运行时调用方 |
|-----|---------------|---------|-------------|
| player_item_dao | item_config_id/level/quality/slot_index/bind_type/expire_time/attrs | item_id/count/position/is_equipped | **0**（唯一"引用"是注释） |
| player_skill_dao | hot_key | is_active | **0** |
| player_buff_dao | stack_count/end_time/caster_id | level/remaining_time/is_active | **0** |
| player_quest_dao | accept_time/complete_time | （无这两列） | **0** |
| auction_dao | seller_name/item_config_id/item_level/item_quality/price_type/price | item_id/starting_price/current_price | **0** |
| player_dao | — | ✅ 完全匹配 | 有（唯一在用的） |

**后果**：这 5 个 DAO 一旦被接进运行时（就像我接背包时那样），CreateItem/UpdateItem 的 INSERT 会因
"未知列"直接报错。当前**全部 0 调用 → 是潜伏的地雷，不是活动 bug**。

**处理（本轮）**：在唯一装配点 `zCommon/db/di/factory.go` 顶加**接线警告横幅**——写明该 DI/Repository 栈
未接线（全仓无 import db/di、db/repository）、这 5 个 DAO 列名与真实表不符、直接启用会报 "Unknown column"、
GameServer 已走 PlayerService 原生 SQL 绕开、接线前必须先对齐 SQL 与共享 model 到真实表。把地雷标在**引爆点**。
**全列对齐 descope**：真正对齐需改 `models.PlayerItem/Skill/...`（多出的 item_config_id/level/quality/…
字段在真实表无列），而这些 model 被 MapServer/auction 复用，改动是跨模块重构而非清理，且栈本身零运行时价值；
故本轮只加警示、不动共享 model。删除整个 DI/Repository 栈亦属架构决策（可能是预留脚手架），留给后续定夺。

### F-2 🟡 战斗经验/等级只落在 MapServer 对象、不回传 GameServer actor → 不持久

`MapServer/maps/combat_handler.go:105` `player.AddExperience(exp)` 改的是 **MapServer 自己的 Player 对象**
（`MapServer/maps/object/player.go` 的 exp/level + LevelUp）。GameServer 侧的 Player **actor** 才是持久化源
（`syncPlayerDataToService` 读 actor 的 level/exp 存盘）。两者是**两份独立表示、属性不同步**——
MapServer 战斗加的经验/升的级**从不回传** GameServer actor（grep 无任何回写路径）。

**后果**：战斗打怪的经验/等级增长跨登录全丢（登出存的是 GameServer actor 的旧值）。非 DB 损坏，
是"战斗进度不持久"。根因=AOI/跨服拆分下，地图侧的属性变更没有回程通道流回持久侧 actor
（对比：血量/死亡有 AOI 广播回程，但那是给旁观客户端看的，不回写 GameServer 持久属性）。
**建议**：中危。要真持久需加 MapServer→GameServer 的属性回写（类似拾取 grant 的 506 通道）；
或按"最小闭环、战斗是 demo"明确 descope 并记录。

## 数据持久化维度（审查所得）

> 根本结构问题：**持久化只有一条完整路径**——客户端显式 `MSG_PLAYER_LEAVE_GAME`→`LeaveGame`→sync+存资产。
> **周期存盘 / 关服 Stop() / 断线 三条路径都不完整**；actor 与 OnlinePlayer 两套状态只在登出那一刻同步一次。

### F-3 🟡→[已修] 关服 Stop() 不 sync actor、不存背包/技能/仓库 → 优雅重启丢在线玩家资产
`player_service.go:327-328` Stop() 只 `savePlayer(online缓存)` 写 players 表，既不先 sync actor→online（会话金币/经验丢），
也不调 `savePlayerAssets`（背包/技能/仓库全丢）。服务器正常重启即丢所有在线玩家的资产与会话增益。
**修复**：`OnBeforeStop` 停网络前调 `LoginService.PersistAllOnline()`——遍历所有在线 actor 先 sync→online、
再 `savePlayerAssets`（背包/技能/仓库）+ `RunOfflineHooks`（清交易/组队会话），最后 `FlushAllOnline` 把 online 缓存写回 players 表。

### F-4 🟡（活动）断线无落库：`OnDisconnect` 0 调用者 → 非正常掉线丢会话 + actor 泄漏
`login_service.go:240` OnDisconnect 定义了但全仓无人调；`LeaveGame` 只被显式 leave 消息触发。客户端崩溃/断网
（不发 leave）→ 既不存盘也不清理，actor 常驻泄漏，周期存盘还持续用其陈旧快照写 players 表。

### F-5 🟡→[已修] 周期存盘/会话中 actor↔online 不同步 → 崩溃丢本会话货币/经验增益
`saveLoop`(30s) 写的是 OnlinePlayer 登录快照（sync 只在登出调一次），对 actor 进度是空转、制造"已定期落库"假象；
崩溃即丢本会话所有 AddGold/邮件/交易 增益。非 DB 覆盖损坏，是崩溃丢增益。
**修复**：PlayerService 加 `syncProvider func()` 回调（services 层不能反向 import game/player，故注入而非直调），
LoginService 构造时注册 `syncAllOnline`（遍历在线 actor→syncPlayerDataToService）。`saveLoop` 周期 tick 在取
`onlineMu.RLock` 前先调 `syncProvider()`（在锁内调会与 SyncOnlinePlayerData 的写锁自锁），使落库的是实时进度。
崩溃丢失窗口从"整场会话"降到"一个存盘周期"（默认 30s，加 `ZMMO_SAVE_INTERVAL` 秒级可调）。actor 属性均 atomic，
跨 goroutine 读安全。**真机 E2E**：B 交易净赚 70→actor 1070，B **全程不登出**，等 3 个 3s 周期后直查 DB=1070
（登出日志=0，证明是周期存盘而非登出写入；修复前该值应为登录快照 1000）。

### F-6 🟡（活动，崩溃窗口）邮件领取跨崩溃净额丢失
`ClaimMail` 先 `UPDATE is_claimed=1`，`mail_handler` 之后才 `p.AddGold` 加到 actor（要登出才落库）。领取后崩溃→
DB 已标已领但金币从未落库→金币凭空消失且不能再领。属 F-5 的特例（附件金币只进内存）。

### F-7 🟢→[已修] 装备(equipment)会销毁物品
`handleEquipItem`：Equip 后从背包 RemoveItem，而 equipment **既不载入也不存盘**、无 DB 表。
一旦装备→登出→重登，该物品在背包和装备两处都不存在=**永久销毁**。但 `NewEquipItemMessage` **0 调用者**、
无客户端注册 → 当前潜伏。**修复**：给 `handleEquipItem` 加失败安全护栏——在补齐 equipment 持久化前一律
返回"装备系统尚未接入持久化，暂不可用"、**绝不触碰背包**（原销毁逻辑已移除）。恢复时删护栏还原即可。

### F-8 🟡 Buff/任务(quest/task) 纯内存无载入无存盘；F-9 🟢 玩家位置纯内存（无 DB 列）。
### F-10 🟢→[已修] VipLevel 与金币同型：登录漏载入 actor（`login_service` EnterGame 缺 SetVipLevel）。**修复**：EnterGame 属性载入块补 `a.SetVipLevel(int32(info.VipLevel))`，防将来 actor 侧 vip 写者被登出零值覆盖。
### F-11 🟢→[已修] `UpdatePlayerGold/Exp/Diamond`(player_service) 直改 online、0 调用者；启用则与 actor AddGold 双写、登出被覆盖。**修复**：删除这 3 个死方法（消除"接线即爆"陷阱），经济数值统一走 actor 侧 API。

> 审查确认：已修的登录载入 + 干净登出回写路径自洽，无残留零值覆盖；未发现"离线玩家被别路径改 players.gold"的并发写者。

## 并发/跨服维度（审查所得）

### T1 🔴→[已修] 交易重复 CONFIRM → ExecuteSwap 跑两次 → 金币翻倍
`trade_manager.go` Confirm 只置位并返回 `ConfirmA&&ConfirmB`，ExecuteSwap 在 handler 锁外执行；网关走 worker pool 并发派发，
一方已确认后重复/并发发两条 CONFIRM → 两个 goroutine 都读到 both==true → **ExecuteSwap 执行两次**（刷币/损币）。
**修复 `Session.completing` 标志**：Confirm 锁内判定「双方确认且未 completing」才 ready=true 并置 completing，
后续重复确认一律 ready=false → ExecuteSwap 恰好一次。加回归测试 `TestTradeManager_DoubleConfirmSingleFire`。

### X1 🔴→[已修] 506 ItemGrant 缺幂等去重（对照 407 有 inbox.TryAccept）→ 重复投递重复发物品
拾取授权回程 506 的 `handleItemGrant` 此前不取 requestID 也不去重，而 attack 407 有 `inbox.TryAccept`。
（注：拾取请求重试因"地图物已移除"天然幂等，但 506 若被重复投递仍会重复发物→防御性对齐 407。）
**修复**：把 `meta.RequestID` 透传进 `HandleItemGrant`，落背包前 `ms.inbox.TryAccept(requestID)` 去重。

### ML1 🟡→[已修] 邮件领取者恰好离线 → DB 已标已领但金币未到账（不可逆丢币）
`ClaimMail` 先 UPDATE is_claimed=1 提交，handler 再把金币加进在线 actor；若此刻领取者已 RemovePlayer（掉线/登出时序），
金币被静默丢弃且 `WHERE is_claimed=0` 使其永不可再领。**修复**：加不到账时 `UnclaimMail` 回滚 is_claimed=0，客户端收失败可重领。

### T2 🟡 交易"确认后改价"被对方在未知情下成交（最小闭环取舍，未改）
`SetGold` 不重置确认（为客户端事件驱动应价稳定收敛而设）。A 确认后改价，B 看到旧值确认即成交用被改后的金额。
真实一致性洞，但属最小闭环取舍。**建议**：生产应让 SetGold 重置双方确认（标准交易安全）。

### T3 🟡→[已修] 交易一方掉线 → 会话悬挂 + 双方被永久锁死无法再交易
`HandlePlayerLogout` 不触碰 tradeManager（handler 私有单例，登出路径无回调可达）。A 交易途中掉线→sessions[A/B] 残留→
A 重登 Start 报"already trading"永久锁死。**修复（统一收口）**：`PlayerManager` 加 `RegisterOfflineHook/RunOfflineHooks`
（RWMutex 快照回调），`TradeHandler` 构造时挂入 `tradeManager.Cancel(pid)+通知对方`；`LeaveGame` 与 `PersistAllOnline` 均调
`RunOfflineHooks`。真机 E2E 验证：A 挂起交易→登出→重登，Start 成功（`Trade started` 而非 already trading）。

### M1 🟡→[已修] 组队同型：成员掉线不清理 playerTeam/teams → 内存泄漏 + 重登被锁"already in a team"
`team_manager.Leave` 是唯一清理入口、仅客户端 LEAVE 触发；登出路径不调。**修复（同一收口）**：`TeamHandler` 构造时挂
`teamManager.Leave(pid)`（未解散则给剩余成员推最新花名册）到同一下线钩子，随 `RunOfflineHooks` 触发。

### M2/M3/X2/T4 🟢 低：离线广播 RouteMessage 安全 no-op；队伍ID重启从1重用(纯内存无DB冲突)；AOI 500-505 覆盖式基本幂等；ExecuteSwap 回滚完整(仅无跨进程事务=已知取舍)。
